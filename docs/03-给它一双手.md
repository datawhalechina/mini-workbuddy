## 3.0 上一章留下的问题

第 2 章末尾说，要让它读你的文件、跑你的命令，就得给它工具。动手之前先看清一件事：眼下这个 Agent 的毛病不只是"不会用工具"，**它还会凭记忆编答案**。

问它"现在几点？"，它会给出一个格式挑不出错、语气笃定的时间，而这个时间没有任何意义。它没有时钟，知识也停在训练数据截止的那一天（1.1 节）。

那它为什么还要答？因为它被训练成"尽量给出有用的回答"。手上没有信息，它就用最像答案的内容填补空白。这个行为叫**幻觉**。

本章要做的，就是让它在不知道的时候，有地方去查。

## 3.1 工具到底是什么

模型只会做一件事：接着你的话往下写文本。没人拦着，它就写一句"现在是下午 3 点 20 分"——编的。

工具要解决的，就是让它在写这句话之前，先"伸手"去取真实数据。

最容易误解的一点：以为 Agent 会自己去查时间。它不会——它只负责写申请单，干活的是框架。

把模型想象成一个被关在隔音玻璃后面的顾问：你能递纸条进去，它只能递纸条出来。它看不见你的电脑，摸不到你的文件，也没有时钟。

所以"调用工具"从头到尾是这样发生的：

1. 你把问题递进去，同时附上一张清单："我这边有这些工具，各自需要什么参数"
2. 顾问递出一张纸条，上面写着：`{"name": "get_current_time", "arguments": {}}`
3. 你（框架）看到纸条，照着执行，拿到"2026-10-30 15:20:33，星期五"
4. 你把结果抄成新纸条递回去
5. 顾问这才写出最终回答："现在是 15:20，星期五。"

顾问从头到尾没碰过时钟。它只写了一张申请单，真正干活的是玻璃外面的你。

### 3.1.1 换成代码里的说法

![一次工具调用的完整往返](assets/ch03/tool-roundtrip.png)

| 步骤 | 谁做的 | 发生了什么 |
|---|---|---|
| 1 | Agent | 组装请求：系统提示 + 历史消息 + 工具清单（JSON Schema），一起发给模型 |
| 2 | 模型 | 只吐出一段文本 `tool_call`：工具名 + 参数 JSON，不是自然语言 |
| 3 | Toolkit | 找到对应工具，校验参数，真正执行 |
| 4 | Agent | 把结果包装成 `ToolResultBlock` 写回上下文 |
| 5 | Agent | 带着新上下文再问一次模型；模型若还要调工具，就回到第 2 步 |

模型在第 2 步输出的东西长这样：

```json
{
  "name": "Read",
  "arguments": { "file_path": "a.txt" }
}
```

它没有读到 `a.txt`，只是说了句"请帮我读 a.txt"；真正打开文件的是第 3 步的 `Read` 工具。

第 2、3 步之间的分界值得停一下：模型只负责"说要做什么"，框架负责"真的去做"——输出 `tool_call` 时世界毫无变化，第 3 步执行完，文件才被打开、命令才跑起来。

想清这一点，三件事就顺了：

- 工具描述写得不好会导致调用失败——模型在第 2 步就选错了工具
- 工具执行报错不会让程序崩溃——错误在第 4 步作为结果回传，让它自己想办法
- 权限拦截可以发生在第 2、3 步之间——申请已经发出，但还没执行

## 3.2 模型怎么知道有哪些工具

靠一份结构化说明书，也就是 3.1.1 第 1 步里那份 JSON Schema。

你不需要手写 JSON。AgentScope 提供了一个适配器 `FunctionTool`：给它一个普通的 Python 函数，它自动完成转换。

下面这段代码可直接运行，不需要 API Key，也不调用模型——它只把函数翻译成 JSON Schema 打印出来。

```python
import asyncio
import json

from agentscope.tool import FunctionTool, Toolkit


def count_text(text: str) -> str:
    """统计一段文本的字符数、中文字数与行数。

    Args:
        text: 需要统计的文本内容。
    """
    if not text:
        return "文本为空。"
    chinese = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
    lines = text.count("\n") + 1
    return f"总字符数 {len(text)}，其中中文 {chinese} 个字，共 {lines} 行。"


async def main() -> None:
    toolkit = Toolkit(tools=[FunctionTool(count_text)])
    schemas = await toolkit.get_tool_schemas()
    print(json.dumps(schemas, ensure_ascii=False, indent=2))


if __name__ == "__main__":
    asyncio.run(main())
```

运行结果（真实输出）：

```json
[
  {
    "type": "function",
    "function": {
      "name": "count_text",
      "description": "统计一段文本的字符数、中文字数与行数。",
      "parameters": {
        "properties": {
          "text": {
            "description": "需要统计的文本内容。",
            "type": "string"
          }
        },
        "required": [
          "text"
        ],
        "type": "object"
      }
    }
  }
]
```

对照着看，你写的东西和模型看到的 JSON 是一一对应的：

![函数如何变成工具定义](assets/ch03/schema-mapping.png)

| 你写的 | 变成了 | 模型怎么用 |
|---|---|---|
| 函数名 `count_text` | `name` | 调用时指名道姓 |
| docstring 的摘要段（`Args:` 之前） | `description` | **判断什么时候该用这个工具** |
| 类型注解 `text: str` | `parameters.properties.text.type` | 构造合法参数 |
| `Args:` 下的说明 | 参数的 `description` | 理解每个参数该填什么 |

补一条：参数带默认值时（`def f(text: str, n: int = 2)`），`n` 不进 `required`——模型据此知道可以不填。

> 完整可运行版本在 `code/ch03/schema_demo.py`，`cd code/ch03 && python schema_demo.py` 即可。
>
> 除了上面这段，它还多跑两个反例：少了类型注解、docstring 写得太敷衍时，schema 会缺成什么样——正好对应 3.6 节的错误 1 和错误 2。

上面这张对照表解释了一个常见现象：**同一个模型，面对两个功能相同的工具，一个调得好、一个却出问题**。差别往往不在代码逻辑，而在 docstring 写得够不够清楚。

> **写工具描述的标准**
> 不是"这个函数做了什么"，而是"**什么情况下应该用它**"。
> 对比这两句：
> - `计算两个数的和` —— 模型得自己判断什么时候该算加法
> - `执行精确的算术运算。当需要计算、核对数字时必须使用本工具，不要心算` —— 模型知道该在什么时候伸手
> 后者长一些，多出来的部分是触发条件。

## 3.3 装配工具

有了函数，还要把它们登记到一个地方。这个登记处就是 `Toolkit`。

```python
def build_toolkit() -> Toolkit:
    return Toolkit(
        tools=[
            FunctionTool(get_current_time),
            FunctionTool(count_text),
            Read(),    # 内置：读文件
            Write(),   # 内置：写文件
            Bash(),    # 内置：执行 shell 命令
        ],
    )
```

`Toolkit` 在本章扮演三个角色：

1. **注册表**：记住有哪些工具
2. **翻译**：把每个工具转成 JSON Schema，每次请求模型时附上
3. **调度员**：模型说要调 `Read`，它负责找到那个 `Read` 实例并执行

前两个角色现在就能验证：`Toolkit.get_tool_schemas()`（异步）直接把"模型看到的世界"打印出来。

完整脚本在 `code/ch03/list_tools.py`，`cd code/ch03 && python list_tools.py` 即可运行，同样不需要 API Key、不调用模型。核心就这几行：

```python
async def print_tool_schemas(toolkit: Toolkit) -> None:
    for schema in await toolkit.get_tool_schemas():
        fn = schema.get("function", schema)
        params = fn.get("parameters", {}).get("properties", {})
        desc = (fn.get("description") or "").splitlines()[0]
        print(f"· {fn.get('name')}")
        print(f"  描述：{desc}")
        print(f"  参数：{list(params.keys()) or '无'}")
```

运行结果（真实输出）：

```
==================================================================
模型能看到的工具清单
==================================================================
· get_current_time
  描述：获取当前的日期和时间。
  参数：无
· count_text
  描述：统计一段文本的字符数、中文字数与行数。
  参数：['text']
· Read
  描述：Reads a file from the local filesystem. You can access any file directly by using this tool.
  参数：['file_path', 'offset', 'limit', 'pages']
· Write
  描述：Writes a file to the local filesystem.
  参数：['file_path', 'content']
· Bash
  描述：Executes a bash command and returns its output.
  参数：['command', 'description', 'timeout']
```

这就是模型在第 1 步收到的全部信息。它没看过你的代码，只看了这五个工具的摘要。

脚本还会额外打印第一个工具的原始 JSON，让你看到摘要背后真正发出去的东西：

```json
{
  "type": "function",
  "function": {
    "name": "get_current_time",
    "description": "获取当前的日期和时间。\n当用户询问\"现在几点\"\"今天几号\"\"星期几\"这类问题时使用本工具。\n你无法感知真实时间，遇到时间问题必须调用本工具，不要凭记忆回答。",
    "parameters": {
      "properties": {},
      "type": "object"
    }
  }
}
```

注意 `description` 是整个**摘要段**，不只第一行：`get_current_time` 没有 `Args:`，三行全在里面。上面那份摘要只截了首行，模型看到的是全文——所以"遇到时间问题必须调用本工具"它真会读到。

（带 `Args:` 的写法不同：`Args:` 以下拆给参数，`description` 只剩第一行，3.2 的输出就是。）

> **一个立刻能做的观察**
> 五个工具，模型的选择空间就是五种。等你加到 30 个工具，它挑错的概率会明显上升。所以自己造工具的时候，名字和描述必须能一句话分清——这是第 6 章的重点。

## 3.4 内置工具

AgentScope 自带一批覆盖常见操作的实现，直接实例化就能用：

| 工具 | 作用 | 只读 |
|---|---|---|
| `Bash` | 执行 shell 命令 | 否 |
| `PowerShell` | Windows 上执行 PowerShell | 否 |
| `Read` | 按行号读取文件，返回带行号的文本 | 是 |
| `Write` | 创建或覆盖文件 | 否 |
| `Edit` | 在文件中做精确字符串替换 | 否 |
| `Glob` | 按文件名模式查找 | 是 |
| `Grep` | 按内容搜索（基于 ripgrep） | 是 |
| `TaskCreate` / `TaskList` / `TaskUpdate` | 维护任务清单 | 否（三个都是） |
| `AskUser` | 向用户提出选择题（2.0.10 可用） | 是 |

> **"能跑代码"用 `Bash`**
> 它没有叫 `run_code` 的工具，`python xxx.py` 走的都是 `Bash`。如果你有一个常用脚本，也可以封装成工具，让它直接调用。
>
> **任务清单那三个工具**：`TaskCreate` / `TaskList` / `TaskUpdate` 让 Agent 把长任务拆成条目、维护状态，第 11 章的右侧面板会用到它们的产出。三个都标"否"，但 `check_permissions` 恒返回 `ALLOW`——整理任务清单不打断你。

表里最重要的不是工具名，是最后一列——"这个工具会不会改变世界"。第 7 章的权限系统就建立在这一列上：只读放行，会写东西的必须拦住。

但"只读"只回答"它改不改东西"，不回答"它能走多远"。`Read` 标着"是"，它的描述却写着 `You can access any file directly by using this tool`——工作区外面的文件它也照读不误。只读不等于不越界，第 4 章 4.2 会拆开讲。

`AskUser` 标"是"，看着和 6.6 节"只读会跳过 `check_permissions`"的说法冲突，其实是两回事：这里说的是框架内置的 `AskUser`，而第 12 章要自己写的 `ask_user` 必须声明 `False`。

`Write` 还有一条容易被忽略的规则：**先读后写**。如果目标文件已经存在而你从未读过它，`Write` 会直接失败。这个设计是为了避免模型在没看到原文的情况下盲目覆盖。

> 你现在可能觉得这条规则碍事。等到第 5 章它替你保住一份重要配置时，你会改变看法。

## 3.5 完整代码

到这里，零件齐了：

- **3.1** 讲清了机制——模型只写申请单，框架才真正执行
- **3.2** 讲了怎么把一个普通函数变成模型能读懂的说明书
- **3.3** 讲了用 `Toolkit` 把工具登记起来
- **3.4** 讲了可以直接拿来用的内置工具

但零件是拆开讲的：`count_text`、`Toolkit` 各自出场，`Read`/`Write`/`Bash` 只在表里露过脸。凑在一起能不能跑，还没验证。

这一节把它们拼成一个完整的 Agent。脚本结构和前两章一样，只多了工具这一层：

| 部分 | 作用 | 对应小节 |
|---|---|---|
| `build_model()` | 连上模型 | 第 1 章 |
| `get_current_time()` / `count_text()` | 两个自定义工具 | 3.2 |
| `build_toolkit()` | 把 5 个工具装进注册表 | 3.3 |
| `print_tool_schemas()` | 打印模型看到的世界 | 3.3 |
| `main()` | 建 Agent，依次问三个问题 | 本节 |

运行前确认 `.env` 里配好了 `OPENAI_API_KEY`（第 1 章已经配过），然后 `cd code/ch03 && python main.py`。

```python
"""第 3 章：给它一双手。

比上一章多了什么：
  1. Toolkit —— 工具注册表
  2. 两个自定义工具（用 FunctionTool 把普通函数变成工具）
  3. 三个内置工具（Read / Write / Bash）
"""

import asyncio
import os
import sys
from datetime import datetime
from pathlib import Path

from dotenv import load_dotenv

from agentscope.agent import Agent
from agentscope.credential import OpenAICredential
from agentscope.message import UserMsg
from agentscope.model import OpenAIChatModel
from agentscope.permission import PermissionMode
from agentscope.tool import Bash, FunctionTool, Read, Toolkit, Write

load_dotenv(override=True)

API_KEY = os.getenv("OPENAI_API_KEY", "")
BASE_URL = os.getenv("OPENAI_BASE_URL", "")
MODEL_NAME = os.getenv("OPENAI_MODEL", "gpt-4o-mini")

def build_model() -> OpenAIChatModel:
    return OpenAIChatModel(
        credential=OpenAICredential(api_key=API_KEY, base_url=BASE_URL or None),
        model=MODEL_NAME,
    )

def get_current_time() -> str:
    """获取当前的日期和时间。

    当用户询问"现在几点""今天几号""星期几"这类问题时使用本工具。
    你无法感知真实时间，遇到时间问题必须调用本工具，不要凭记忆回答。
    """
    now = datetime.now()
    week = "一二三四五六日"[now.weekday()]
    return now.strftime("%Y-%m-%d %H:%M:%S") + f"，星期{week}"

def count_text(text: str) -> str:
    """统计一段文本的字符数、中文字数与行数。

    Args:
        text: 需要统计的文本内容。
    """
    if not text:
        return "文本为空。"
    chinese = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
    lines = text.count("\n") + 1
    return f"总字符数 {len(text)}，其中中文 {chinese} 个字，共 {lines} 行。"

def build_toolkit() -> Toolkit:
    """把工具装配成一个 Toolkit。"""
    return Toolkit(
        tools=[
            FunctionTool(get_current_time),
            FunctionTool(count_text),
            Read(),
            Write(),
            Bash(),
        ],
    )

async def print_tool_schemas(toolkit: Toolkit) -> None:
    """打印工具清单——这就是模型在每次推理前看到的东西。"""
    print("=" * 66)
    print("模型能看到的工具清单")
    print("=" * 66)
    for schema in await toolkit.get_tool_schemas():
        fn = schema.get("function", schema)
        params = fn.get("parameters", {}).get("properties", {})
        desc = (fn.get("description") or "").splitlines()[0]
        print(f"· {fn.get('name')}")
        print(f"  描述：{desc}")
        print(f"  参数：{list(params.keys()) or '无'}")
    print()

async def main() -> None:
    # 把工作目录切到本章脚本所在目录，这样模型写出的 fizz.py 会落在 code/ch03/，
    # 后面 `python fizz.py` 也能直接找到它。
    os.chdir(Path(__file__).resolve().parent)

    toolkit = build_toolkit()
    await print_tool_schemas(toolkit)

    agent = Agent(
        name="Buddy",
        system_prompt=(
            "你叫 Buddy，是一个住在命令行里的工作助手。"
            "需要用工具获取信息时必须调用工具，不要凭记忆猜测。短答即可。"
        ),
        model=build_model(),
        toolkit=toolkit,
    )

    # 这一章的脚本没有确认界面。Bash 这类工具默认会"停下来等人点头"，
    # 在这个没有界面的场景里就会卡住，后面再发消息还会报错。
    # 先整体放行，把注意力放在"工具能不能用起来"；第 7 章专门讲怎么管住它。
    agent.state.permission_context.mode = PermissionMode.BYPASS

    # 让 shell 里的 python 一定是当前这个解释器。
    os.environ["PATH"] = os.path.dirname(sys.executable) + os.pathsep + os.environ.get("PATH", "")

    questions = [
        "现在几点？今天星期几？",
        "帮我数一下这句话有多少字：今天天气不错，适合写代码。",
        # 第三问故意让它"写 + 跑"：一次触发 Write、Bash 两个工具。
        "把 1 到 20 的 FizzBuzz 写成 fizz.py，"
        "然后用 python fizz.py 跑一遍，把标准输出原样贴给我。",
    ]

    for question in questions:
        print(f">>> 你：{question}")
        reply = await agent.reply(UserMsg(name="user", content=question))
        print(f"<<< Buddy：{reply.get_text_content()}")
        print()

if __name__ == "__main__":
    asyncio.run(main())
```

跑起来后，屏幕上先出现 3.3 节那份工具清单，然后是三问三答。前两问很短，模型各调一次工具就收工（时间以你跑出的为准）：

```
>>> 你：现在几点？今天星期几？
<<< Buddy：现在是 2026-10-30 15:20:33，星期五。

>>> 你：帮我数一下这句话有多少字：今天天气不错，适合写代码。
<<< Buddy：总字符数 13，其中中文 11 个字，共 1 行。
```

这两句里的时间、字数都不是模型算的，是工具返回值回传后它照着念的。到这一章，Agent 才第一次真正"知道"外部世界的事。

前两问只是"查一下"，答完就结束。第三问不一样：Agent 会在你电脑上生成脚本，还真调起解释器跑一遍。

```
>>> 你：把 1 到 20 的 FizzBuzz 写成 fizz.py，然后用 python fizz.py 跑一遍，把标准输出原样贴给我。
<<< Buddy：`fizz.py` 已创建在 `code/ch03/`，运行 `python fizz.py` 的标准输出：

1

Fizz
4
Buzz
Fizz
7

Fizz
Buzz
11
Fizz
13
14
FizzBuzz
16
17
Fizz

```

这一问里，3.1 节那个循环转了**两圈**：

- 第一圈，模型输出 `Write` 的申请单，框架把 `fizz.py` 写到磁盘
- 第二圈，模型输出 `Bash` 的申请单，框架执行 `python fizz.py`

那 20 行输出不是模型"写"出来的。它只知道"我请框架跑了一条命令"，输出是第 4 步回传进上下文的。**它和你几乎同时看到这些数字。**

想看申请单本身，把 `reply()` 换成第 2 章的 `reply_stream()`，模型每递一张单就吐一组 `TOOL_CALL_*` 事件。

**"能执行代码"不是一项独立能力。** `python fizz.py` 走的就是 3.4 表里第一行那个 `Bash`；`pytest`、`npm run build`、`git commit` 全是同一条路。把 `Bash` 从 Toolkit 里删掉，本章的 Agent 立刻退回"只会读写文件"。

### 3.5.1 代码里的三个细节

上面这段代码能跑通，靠三处不显眼的写法。

**细节 1：`system_prompt` 里那句"必须调用工具"。**

就是 `Agent(...)` 里 `system_prompt` 的第二句。它不是装饰。模型有很强的"直接回答"倾向，尤其面对简单问题；明确要求它信息不足时调用工具，能显著降低幻觉率。最实用的一条提示词技巧：**给模型一条撤退路线，它才不会硬编**。

**细节 2：`PermissionMode.BYPASS` —— 先放行，第 7 章再管。**

就是 `main()` 里那行 `agent.state.permission_context.mode = PermissionMode.BYPASS`。

给了 `Bash`，它就能直接操控你的电脑——真的可以删掉硬盘里的文件。用过 WorkBuddy 的话，你见过它停下来问"是否允许执行"，那就是权限系统。

本章脚本没有确认界面，`Bash` 默认会"停下来等人点头"，不处理就会卡死。所以这里先整体放行，把注意力放在"工具能不能用起来"。`PermissionMode` 的细节不用深究，第 7 章会讲怎么把它管住——那时你会把这行删掉。

> 问题写死在代码里、不做成 `input()`，也是这个原因：每次跑出来都一样，也不会有人随手输入"帮我清理下磁盘"，让 AI 真去删文件。

**细节 3：AI 是怎么知道 Python 解释器在哪里的**

Agent 执行脚本，本质上是在终端里跑了一句 `python xxx.py`。那它怎么知道你电脑上的解释器在哪里？

模型在第 2 步输出的申请单，内容就是一句 `python fizz.py`。它不知道你的 Python 装在 `E:\anaconda` 还是 `C:\Python312`，只是照着"人类一般这么敲"写了一句命令。

真正把 `python` 变成"某个具体的 exe"的，是第 3 步执行命令的那个 shell（工具名叫 `Bash`，在 Windows 上框架实际用 `cmd /c` 执行）。shell 拿到 `python` 后，会去环境变量 `PATH` 里列出的目录中**按顺序挨个找**，找到第一个 `python.exe` 就用它。

那代码里这行是干什么的？

```python
os.environ["PATH"] = os.path.dirname(sys.executable) + os.pathsep + os.environ.get("PATH", "")
```

`sys.executable` 是当前正在运行 main.py 的那个解释器的完整路径。这行把它所在的目录插到 `PATH` 最前面，于是 shell 找 `python` 时第一个就撞上它。

为什么非要这么做？因为 Python 装在哪里因人而异，`PATH` 里的 `python` 也未必就是跑 main.py 的那一个——插这一行，等于把"我正在用的解释器"钉死给模型。

那让模型在命令里直接写绝对路径行不行？路径含空格就得加引号，而带引号的命令经 shell 转发时，引号常被当成命令名的一部分（Windows 实测直接报"不是内部或外部命令"）；不加引号，空格又把命令拆成两段。命令里只留 `python` 一个词，这些就都绕开了。

> 卡住的话补一句：解释器就是把 `xxx.py` 读进去、一行行执行的可执行文件（Windows 上叫 `python.exe`），`.py` 只是它的输入。

### 3.5.2 模型写错了代码，会怎样

假设它生成的 `fizz.py` 里少了个冒号：

```python
for i in range(1, 21)
    print(i)
```

`Write` 照写不误——它只负责写，不检查语法。接着 `Bash` 执行 `python fizz.py`，解释器报 `SyntaxError`；这段 stderr 会连同 `Command failed` 一起作为工具结果回传，不会被框架吞掉。模型在下一轮上下文里"看得见"自己错在哪，于是补上冒号、再写、再跑。

写代码 → 跑起来 → 看报错 → 改代码，这个循环一旦转起来，Agent 就能自己修错。这也是 3.1 节那个循环最有价值的地方：错误不是终点，而是下一轮的输入。

## 3.6 三个常见错误

**错误 1：函数没有类型注解**

```python
def count_text(text):        # 少了 : str
    ...
```

生成的 schema 里 `required` 照样列着 `text`，但它的定义塌成了一个空对象 `{}`——没有 `type`，也没有参数说明。模型知道有个叫 `text` 的参数，却不知道它该填字符串还是数字。表现是工具确实被调用了，参数却常常填得不对。

**错误 2：docstring 只写了函数名**

```python
def count_text(text: str) -> str:
    """统计文本。"""
```

"统计文本"这四个字，模型无法判断该在什么时候用：统计字数？统计词频？统计行数？结果就是它该用的时候不用，不该用的时候乱用。

写 docstring 的时候，把自己当成在跟一个刚入职的同事交代工作：**什么情况用、输入是什么、输出是什么**。

**错误 3：工具返回了非字符串**

```python
def get_stats(text: str) -> dict:      # 返回 dict
    return {"chars": len(text)}
```

工具的执行结果最终要作为文本进入模型的上下文，框架只做一层兜底：能 `json.dumps` 的就转成 JSON，不能的退成 `str()`。于是 `None` 变成 `null`，自定义对象变成 `<Obj>`，异常对象变成 `boom`——都不报错，但信息已经走样。模型看到一个 `null`，读不出"这次统计失败了"，很可能当成"没有数据"接着往下编。

**统一返回字符串**，措辞由你控制；确实要给结构化数据，自己 `json.dumps(..., ensure_ascii=False)`。

## 3.7 小结

- 工具的实质是**模型输出一段结构化申请，框架代它执行**
- `FunctionTool` 把函数名、docstring、类型注解转成模型能读的 JSON Schema
- docstring 要写"什么情况下用它"，而不是"它做了什么"
- `Toolkit` 是注册表、翻译、调度员三合一
- 执行代码没有专用工具：`Bash` / `PowerShell` 就是。写代码 → 跑起来 → 看报错，是检验工具链最短的一条路

**下一章要解决的问题**：3.1.1 的表格最后一行写着"带着新上下文再问一次模型；模型若还要调工具，就回到第 2 步"。这一轮到底转了几次、什么时候停、停不下来怎么办——这就是 ReAct 循环，也是整套框架真正的心脏。
