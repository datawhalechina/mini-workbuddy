# 第 9 章　会话要活下去

> 本章代码 `code/ch09/probe_state.py`、`code/ch09/store.py`、`code/ch09/main.py`　·　读完约 4 分钟

## 9.0 记忆存在哪儿

第 8 章结尾说过，上下文、权限规则、你交代过的偏好，全挂在内存对象上，关掉终端一切归零。

原因在模型这侧。模型本身无状态，它不记得上一轮说过什么。你看到的"它记得"，是框架每次发请求前把整段历史重新拼进 prompt。

所以第 8 章结尾那个问题可以答了。有状态的不是 `Agent`，是 `AgentState`。`Agent` 只是个壳，配置加一个指向 state 的引用：

```python
Agent(name=..., system_prompt=..., model=..., toolkit=..., state=state)
```

传进去哪份 state，它就接着哪段对话聊。换一份，就是另一个会话，同一个进程里几份 state 并排跑，互不打扰。

本章要解决的只有一件事，把 state 写成文件，下次启动再读回来。

## 9.1 存：一个文件

`AgentState` 是 pydantic 模型，自带序列化，不用手写转换函数。

```python
state.model_dump_json(indent=2)      # → 一整段 JSON 字符串
```

剩下的就是文件读写。`store.py` 去掉写元信息的部分，骨架是这样：

```python
class JsonStateStore:
    def __init__(self, root: str = ".sessions"):
        self.root = root

    def _path(self, user_id, agent_id, session_id):
        return os.path.join(self.root, user_id, agent_id, f"{session_id}.json")

    def save(self, user_id, agent_id, state):
        path = self._path(user_id, agent_id, state.session_id)
        os.makedirs(os.path.dirname(path), exist_ok=True)
        with open(path, "w", encoding="utf-8") as f:
            f.write(state.model_dump_json(indent=2))

    def load(self, user_id, agent_id, session_id):
        path = self._path(user_id, agent_id, session_id)
        if not os.path.exists(path):
            return None
        with open(path, encoding="utf-8") as f:
            return AgentState.model_validate_json(f.read())
```

一条会话一个文件，路径长这样：

```text
.sessions/<user_id>/<agent_id>/<session_id>.json
```

三层目录对应三个问题，谁在聊、跟哪个智能体聊、聊的哪一段。三个键里只有 `session_id` 需要生成，`AgentState` 会自己造一个 32 个十六进制字符的串，也可以在创建时指定。

对话、任务、权限规则全装在这一个文件里。任务指的是 `TaskCreate` 那套清单工具维护的条目，本章拿它验证另一件事，任务也会跟着会话一起活下来。文件不大，`probe_state.py` 存一条消息加两条任务，落地 1866 字节。

> `store.py` 还会多写一个 `.meta.json`，里面只有标题、更新时间、消息条数、任务条数、摘要长度。会话列表页读它就够了，不必为了列一张表把每条会话的完整 JSON 都翻一遍。删会话时两个文件要一起删。

用文件是为了不引依赖。想换 Redis 或数据库也可以，上层只用到 `save` / `load` 两个方法，换掉实现不影响别处。

## 9.2 取：启动时接回去

```python
state = store.load(USER_ID, AGENT_ID, session_id)   # 读文件，没有就返回 None
agent = await build_agent(workspace, state)         # 造 Agent，把 state 递进去
```

`state=None` 时框架造一个空 state，等于新会话；读到了，就是接着上次聊。

一轮聊完存一次：

```python
await chat_once(agent, "记住：我的周报固定分三段，进度、问题、下周计划。")
store.save(USER_ID, AGENT_ID, agent.state)
```

`main.py` 就是这么串的，两轮对话，每轮结束存一次盘，收尾时把会话列表打出来。首次运行它会打印会话 id，下次启动带上这个 id 就能接着聊：

```bash
cd code/ch09 && python main.py 8afdedb7b46d431dbe67be1dd71b74ef
```

重启之后不用你再提，Buddy 也知道周报分三段，上一轮建的三个任务也还在。

不碰模型也能看清这套机制在跑：

```bash
cd code/ch09 && python probe_state.py
```

## 9.3 两处容易踩空

**每轮存一次，别等退出。**

"退出时存"这个时机不可靠，进程可能被 kill，异常可能直接终止，两条路都轮不到你的收尾代码。哪里状态变了就在哪里落盘，最坏只丢最后一轮。

代价是每存一次都要重写整份文件。demo 这个体量无所谓，会话一长就成了纯浪费，那时候再换增量写或者数据库。

**读回来要清三个字段。**

`store.load()` 读完文件后多写了三行：

```python
state.reply_context.structured_schema = None
state.reply_context.structured_output = None
state.reply_context.cur_iter = 0
```

序列化本身是无损的，但"上一轮是对的"不等于"这一轮也是对的"：

- `structured_schema` 是上一轮要求过的输出格式。留着它，恢复之后你问一句"今天几号"，模型也会被逼着按旧格式交 JSON。
- `structured_output` 是上一轮那份结构化结果。留着它，模型会以为这次的结果已经交过了。
- `cur_iter` 记的是"这一轮走到第几步"。被强杀时它会停在非零值，留着它，Agent 以为这一轮还没结束，轮次开始时该做的检查（注入时间、刷新工具状态）整个跳过，而且不报错。

工具状态（`tool_context`）反过来，要原样留着。它记的是这个会话里哪些工具已激活、哪些分组开着，跟对话记录一样属于会话的一部分。顺手清掉，恢复之后模型拿到的是一套陌生的工具集。

## 9.4 小结

- 无状态的是模型，有状态的是 `AgentState`；`Agent` 只是壳，换份 state 就换段对话
- 存用 `model_dump_json()`，取用 `model_validate_json()`
- 一条会话一个文件，`user_id` / `agent_id` / `session_id` 三级目录
- 状态一变就落盘，别等进程退出
- 读回来清 `structured_schema`、`structured_output`、`cur_iter`，`tool_context` 留着
